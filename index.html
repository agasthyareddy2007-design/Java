How Java Runs

1. Java Source Code

A programmer writes Java source code in a .java source file. The source code is human-readable and contains classes, methods, variables and instructions.

2. Compilation

The Java compiler, javac, translates the source code into Java bytecode.
.java → javac → .class
The resulting .class file contains bytecode rather than processor-specific machine instructions.

3. Bytecode

Bytecode is an intermediate instruction format designed to be executed by the JVM. It is not directly tied to Windows, Linux, macOS or one specific CPU.

4. Class Loading

The JVM's Class Loader loads the required classes into memory. The JVM then verifies and prepares the classes before they are used.

5. Runtime Memory

While the program runs, the JVM uses different Runtime Data Areas such as: Heap, Stack, Method Area, PC Register, Native Method Stack.

6. Execution

The Execution Engine executes the bytecode. The JVM can interpret bytecode and can also use the JIT Compiler to compile suitable code into native machine code.

7. Native Execution

The resulting execution ultimately occurs on the current machine through the platform-specific JVM implementation.

JVM Components Overview

CLASS LOADER

The Class Loader subsystem loads Java class files into the JVM when they are required. It identifies classes, loads their bytecode and participates in preparing those classes for execution.

It also provides the mechanism through which different classes become available to the running Java program.

RUNTIME DATA AREAS

Runtime Data Areas are the memory regions used by the JVM while a Java program is executing. Different areas have different responsibilities, such as storing objects, active method calls, class information and the current instruction being executed.

EXECUTION ENGINE

The Execution Engine is responsible for executing Java bytecode. The Interpreter can execute instructions directly, while the JIT Compiler can translate suitable bytecode into native machine code to improve execution performance.

The Garbage Collector also works with the runtime memory by reclaiming memory occupied by objects that are no longer reachable.

Class Loader

Loading

The Class Loader finds the required class and loads its bytecode into the JVM.

Linking

The JVM verifies the loaded class and prepares the runtime structures needed for it. Linking can be understood through three conceptual steps:

  • Verification — checks that the class structure and bytecode are valid.
  • Preparation — prepares memory for class-level/static data.
  • Resolution — resolves symbolic references when required.

Initialization

The JVM initializes the class, including required static initialization.

The result is a class that is ready to be used by the running program.

JVM Memory Components

METHOD AREA

Stores information associated with loaded classes.

  • Class and method information
  • Runtime representation of class structure
  • Static variables/data
  • Information required by the JVM when executing class methods

HEAP

The main runtime memory area for objects and arrays.

  • Objects are created here
  • Arrays are stored here
  • Shared by threads
  • Garbage Collector manages reclaiming unreachable object memory

STACK

Each thread has its own JVM stack.

  • Contains stack frames for active method calls
  • Stores local variables and method execution information
  • A new frame is created when a method is called
  • The frame is removed when the method returns

PC REGISTER

Tracks execution for each thread.

  • Identifies the current JVM instruction
  • Each thread has its own PC Register

NATIVE METHOD STACK

Supports native method execution.

  • Used while native methods execute
  • Separate from the normal Java bytecode stack

JIT Compiler

WHAT IS JIT?

The Just-In-Time compiler is part of the JVM's Execution Engine. It converts suitable Java bytecode into native machine code while the program is running.

This means the JVM does not necessarily need to interpret every instruction in the same way for the entire lifetime of the program.

WHY DOES THE JVM USE JIT?

Interpreting bytecode instruction by instruction provides flexibility, but repeatedly interpreting the same code can introduce execution overhead.

The JIT Compiler can identify code that is executed repeatedly and compile it into native machine code. That native code can then be executed directly by the processor.

Key Idea

The JVM combines interpretation + runtime compilation rather than relying on only one execution technique.

Garbage Collection

WHAT IS GARBAGE COLLECTION?

Garbage Collection is the JVM's automatic memory-management mechanism for reclaiming memory occupied by objects that are no longer reachable by the running program.

The programmer does not normally need to manually free Java objects.

WHY IS IT NEEDED?

Objects are continuously created while a Java program runs.

Some objects eventually become unreachable because there are no longer any references that can access them. That memory can then be reclaimed by the Garbage Collector.

Platform Independence

Core Idea

Java source code is compiled into bytecode rather than directly into machine code for one specific operating system. The bytecode can then be executed by a JVM implementation designed for the target platform.

  • 1. Source code is compiled once — The Java compiler converts .java into .class bytecode.
  • 2. Bytecode is platform-independent — The bytecode is not tied to a particular operating system or processor architecture.
  • 3. JVM is platform-specific — Windows, Linux and macOS use JVM implementations appropriate to their respective platforms.
  • 4. JVM provides the execution environment — The JVM interprets or compiles the same bytecode for the target system.
  • 5. Same bytecode, different environments — A compiled Java program can be moved between compatible systems without recompiling.
  • 6. The JVM handles the specifics — Platform independence does NOT mean the JVM is identical everywhere. The bytecode is portable; the JVM handles the OS details.
